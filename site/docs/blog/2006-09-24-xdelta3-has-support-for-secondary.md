Xdelta3 has support for <b>secondary compression</b>, part of VCDIFF (<a href="http://www.rfc-editor.org/rfc/rfc3284.txt">RFC 3284</a>) that allows external compression algorithms for the three parts of a VCDIFF window (<tt>instruction</tt>, <tt>address</tt>, <tt>data</tt>). VCDIFF is entirely based on byte codes, not variable-length codes.<br /><br />Most compression programs are based on <a href="http://en.wikipedia.org/wiki/Huffman_coding">Huffman coding</a>, and there's the well-known <a href="http://en.wikipedia.org/wiki/Burrows-Wheeler_transform">Burrows&ndash;Wheeler</a> transform implemented by <a href="http://www.bzip.org">bzip2</a>. But there's more to it. I asked Julian Seward and he pointed me at two very interesting articles by <a href="http://www.thocp.net/biographies/wheeler_david.htm">D. J. Wheeler</a>. <br /><br />The <a href="ftp://ftp.cl.cam.ac.uk/users/djw3/bred3.ps">decription</a>, and the <a href="ftp://ftp.cl.cam.ac.uk/users/djw3/bred3.c">code</a>. Fascinating.<br /><br />The algorithm works with multiple Huffman-code tables and several iterations. The input is divided into fixed-length chunks, each chunk assigned to a Huffman table. Each iteration, chunks are assigned to the table which gives the shortest encoding, then the tables are recomputed according to the chunks they were assigned.<br /><br />The chunk encodings plus the chunk&ndash;table assignments are then transformed by <a href="http://en.wikipedia.org/wiki/Move-to-front_transform">move-to-front</a>. Move-to-front works very well (especially following Burrows&ndash;Wheeler), but it presents another problem for later Huffman coding, because after move-to-front coding there tend to be many <tt>0</tt>s, and a symbol having frequency greater than 50% will not be efficiently encoded by Huffman coding&mdash;even the shortest 1-bit code has redundency. To address this problem, the <tt>0</tt> symbol is replaced by two symbols (call them <tt>0_0</tt> and <tt>0_1</tt>).  These two symbols are used to code the run-length of <tt>0</tt>s in binary.<br /><br />What really fascinates me is how Wheeler does this in <a href="ftp://ftp.cl.cam.ac.uk/users/djw3/bred3.c">780 lines of code</a>&mdash;including the Burrows&ndash;Wheeler transform. Amazing.<br /><br />Xdelta3 has a secondary compressor based on DJW enabled by <tt>-S djw</tt> (<a href="http://xdelta.googlecode.com/svn/trunk/xdelta3/xdelta3-djw.h">2000 lines</a> w/ no Burrows&ndash;Wheeler transform).  For comparison (*), there's another secondary compression (enabled by <tt>-S fgk</tt>), based on D. E. Knuth's <a href="http://portal.acm.org/citation.cfm?coll=GUIDE&dl=GUIDE&id=4008">Dynamic Huffman coding</a>. A dynamic huffman code updates code-table frequencies after each symbol is encoded or decoded. The routines are efficient (it's Knuth, after all), but still slower than DJW.<br /><br />Since there are no standards written for secondary compression, secondary compression is turned off by default, but I recommend giving <tt>-S djw</tt> a try.
