Re: Xdelta 3.0p (<a href="http://code.google.com/p/xdelta/downloads/list">download</a>)<br /><br />Xdelta-3.x processes a window of input at a time, using a fixed memory budget.  This release raises some of the default maximums, for better large-file compression. The default <a href="http://code.google.com/p/xdelta/wiki/TuningMemoryBudget">memory settings</a> for large files add up to about 100Mb. (*)<br /><br />A user wrote to confirm good performance on 3.7Gb <a href="http://code.google.com/p/xdelta/issues/detail?id=23">WIM</a> files, great!<ul>So, to answer the question in your <a href="http://xdelta.org/2007/01/re-xdelta-1.html">post on Jan 28th</a>, yes we are using xdelta3 with files larger than 1Gb and it's working well.<br /><br />I'm off to try boosting the compression and see how much we can scrunch the patch down. Thank-you for an extremely useful tool that is going to hugely improve our ability to distribute updates to our build images.</ul>At the other extreme, a developer wrote to ask about using xdelta3 in the <a href="http://www.xensource.com/xen/">Xen</a> kernel. Here's an <a href="http://xdelta.googlecode.com/svn/trunk/xdelta3/examples/small_page_test.c">example</a> of xdelta3 configured for a 4Kb page using 32Kb.<br /><br />A user writes about code size:<ul>I saw your post where you said you’d improved the compression in Xdelta3 and that it was now slightly faster than 1.1.  Do you happen to know where the two stand without compression enabled?  (We don’t use Xdelta’s compression because we compress all of our files after the fact with Rar solid compression.)  Thanks too for the link to those benchmarks.  Those were quite helpful, and it’s cool to see Xdelta come out on top. ;)<br /><br />I will say this: One nice thing about the new Xdelta is its smaller size!  Xdelta 1.1’s exe is 1Mb when not compressed via UPX, whereas Xdelta3 is 100Kb.  Nice. :)</ul>Thanks! Xdelta3 is faster and better than Xdelta1 with compression disabled (the <tt>-0</tt> flag), thanks to <a href="http://www.faqs.org/rfcs/rfc3284.html">VCDIFF</a> and other improvements.<br /><br />I'm looking for your ideas on <a href="http://code.google.com/p/xdelta/issues/detail?id=21">recursive directory diff</a>. One solution uses tar:<ul><tt>XDELTA="-s source" tar --use-compress-program=xdelta3 -cf ...</tt></ul>This approach is better than computing pairwise differences, since data can be copied across files/directories. Pay attention to file order and source buffer size. Microsoft developers, consider using the <a href="http://en.wikipedia.org/wiki/WIM_image_format">WIM</a> disk image format.<br /><br />Thanks for the feedback (file a new <a href="http://code.google.com/p/xdelta/issues/entry">issue</a>).<br /><br />(*) Xdelta-1.x processes the whole input at once, and its data structure takes linear space, <tt>(source file size/2)+O(1)</tt>.  Xdelta-1.x reads the the entire source file fully two times (to generate checksums, to match the input), using at least half as much memory as the source file size.
